# Contributing

Contributions are welcome through focused issues and pull requests. Version 3 deliberately has one owner for each product invariant: `src/coordinator/install`, `state`, `routing`, `dashboard`, and thin `cli` adapters. Preserve those boundaries and the no-project-footprint contract.

## Development

Use Python 3.11 or newer. The runtime has no third-party dependencies.

Install the pinned development-only linter in a disposable environment:

```sh
python3 -m pip install ruff==0.16.2
```

Run the repository checks:

```sh
python3 -m unittest discover -s tests -v
python3 -m compileall -q src skill/scripts tools tests
ruff check --no-cache src skill/scripts tools tests
```

Package and installer changes belong in `tests/test_package.py` and `tests/test_install.py`. Installer tests must use an isolated home and the public `--source` behavior; do not add a hidden installation bypass.

Add the smallest decisive test for a changed public contract. Avoid duplicate cross-layer assertions, broad fixture frameworks, generated bytecode, credentials, release outputs, or user-specific paths in commits.

## Pull requests

Describe the observable change, owner, compatibility impact, and exact checks run. Breaking behavior requires a major-version decision. Security-sensitive findings should follow [SECURITY.md](SECURITY.md), not a public issue.

## Maintainer release

Keep `main` protected by the lint check and the Linux, macOS, and Windows Python 3.11 checks. The `trusted-agentic-e2e` and `release` environments require approval; only the release publish job receives `contents: write`. Store `OPENAI_API_KEY` exclusively as a `trusted-agentic-e2e` environment secret and enter it interactively with `gh secret set OPENAI_API_KEY --env trusted-agentic-e2e`.

Prepare a release through a pull request that updates `VERSION`, `pyproject.toml`, both runtime version constants, and `CHANGELOG.md`. After required CI and the trusted E2E pass on the merged commit, create and push an annotated `v<version>` tag at that exact commit. The release workflow validates the tag against `VERSION`, builds the three public assets, publishes them, and reads the resulting asset set back.

Never bypass a failed check, move or delete a public tag, overwrite a release, or replace an asset in place. Fix defects forward with the next SemVer patch.
